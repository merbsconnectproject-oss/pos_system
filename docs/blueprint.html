01 Decision record

Each of these was reached by working a constraint until it forced an answer. The struck→ entries are positions held earlier in planning and since overturned — recorded so nobody re-argues them from the old documents.

Language Java 21 · Spring Boot 3 Settled
TypeScript / Node→Java

The developer who will hold the pager writes Java. That outweighs the convenience of importing the frontend's rules directly. The reusable frontend logic is roughly 520 lines — three to four days to port — against which Spring Security, Flyway, @Lock(PESSIMISTIC_WRITE), Bean Validation, BigDecimal and Testcontainers give back comparable time on work the plan already schedules.

Topology Local-first, one instance per shop Settled
Cloud, shared instance→Local per outlet

The application and its database run on the counter PC. Each shop is self-contained. This deletes the two hardest deliverables in the original plan — the offline queue and the separate print service — and removes the connectivity dependency that was the project's top risk. The cost is the owner's consolidated view, which is deferred.

Database PostgreSQL 18, installed locally Settled

Not SQLite and not H2. Identical schema, identical Flyway migrations and identical SQL mean that going online later is a connection string plus a sync layer, rather than a rewrite. Postgres on Windows is a routine install and sits at roughly 250 MB.

Persistence Spring Data JPA + JdbcTemplate Settled

JPA for transactional paths, where @Lock(PESSIMISTIC_WRITE) expresses BR-8 directly. Plain JdbcTemplate for the sixteen reports, so aggregations are written as SQL instead of fought through an ORM. Flyway owns the schema; Hibernate never generates DDL.

Primary keys UUID everywhere Settled

The single most consequential choice in this document. Two local databases both counting from 1 will collide catastrophically if they are ever merged into one cloud instance. UUIDs make that merge a weekend instead of a migration project. The PRD already puts uuid UNIQUE on sale BR-7; this extends it to every table as the actual primary key.

Printing In-process, via javax.print Settled
Separate Go/Windows service→In-process

Once the server runs on the counter PC there is nothing for a separate print service to bridge. ESC/POS bytes go straight to the Windows spooler in RAW mode from the same process that completed the sale. One deliverable and one installer disappear.

Hosting None. Nightly backup to Cloudflare R2 Settled
Railway · ~$96/yr→$0 + free-tier R2

With no server there is no hosting bill. The only recurring infrastructure is an off-site backup target, and a day's trading compresses to a couple of megabytes — comfortably inside R2's free tier for the life of the system.

Offline Native, not a queue Settled

FR-SYNC-08 — full-day offline — was a Stage 3 could-have priced separately. Local-first delivers it as a property of the architecture rather than a feature, and simultaneously satisfies NFR-2, NFR-4 and NFR-5 without an offline queue existing at all.

Typography Persisted keys, fixed browser stacks Settled

Appearance stores a font key and a bounded 90–130% scale beside the accent colour. The API accepts only Jakarta, System, Arial, Verdana or Georgia keys; the browser maps them to fixed fallback stacks. Arbitrary CSS and remote font URLs never enter settings, while every terminal receives the same readable appearance.

The frontend is built by Vite and copied into src/main/resources/static, so it ships inside the same JAR. No separate web host, no CORS, no cross-origin cookie question — which retires the week-one decision the original plan flagged as a rework risk.

Why this fits the business

One checkout terminal per outlet AS-4 and non-overlapping catalogues mean each terminal is the sole writer to its own shop's stock. The hardest part of offline POS — reconciling concurrent writers — does not exist here. The architecture matches how the shops actually trade.

Constraints that carry business meaning

These are not incidental indexes. Each one is a business rule the database enforces so that no code path can bypass it.

  • UNIQUE(shift.user_id) WHERE status='open' and UNIQUE(shift.terminal_id) WHERE status='open' — one open shift per user and per terminal BR-13
  • UNIQUE(sale.uuid) and UNIQUE(payment.uuid) — idempotency on retries BR-7
  • UNIQUE(sale.receipt_number) — gapless, never reused BR-6
  • CHECK(stock_level.quantity_base >= 0), lifted only on the explicit flagged oversell path BR-9
  • UNIQUE(product.sku), UNIQUE(product_barcode.barcode), UNIQUE(customer.phone)
  • Trigram index on product(name, sku, description) for the 300 ms search target NFR-1
Local-first makes NFR-1 easier

The 300 ms search target was written against a network round trip to a shared catalogue of 3,000 products. On a local Postgres, serving only the slice its own shop stocks, the working set sits in shared buffers and the query never leaves the machine.

BR-8 still matters — for a different reason than the PRD gives

With one terminal per outlet and non-overlapping catalogues, two terminals can never contend for the same stock_level row. The lock earns its keep on a path the PRD does not name: the storekeeper receiving goods on a tablet while the cashier sells the same product at the till. That happens weekly. Test that, not a two-terminal race that cannot occur.

05 The drift problem

Two languages now enforce the same money and permission rules. Drift between them is the failure mode that produces unexplainable shift variances months after go-live — small, intermittent, and very expensive to diagnose. This section is the defence.

The rounding mismatch, measured

money.ts nudges with Number.EPSILON to defeat float error. Near 100 the gap between doubles is roughly 1.4 × 10⁻¹⁴ — far larger than EPSILON — so the nudge does nothing and the value rounds down. Java's BigDecimal rounds up. Run against the real implementation:

Inputmoney.ts todayBigDecimal HALF_UPVerdict
0.1250.130.13agree
2.6752.682.68agree
1.1151.121.12agree
1.0051.001.01Differs
0.1450.140.15Differs

Java is the one that is correct. Replicating the JavaScript bug would be the wrong fix — change the frontend instead. Normalising the scaled value before rounding brings money.ts into agreement on every case tested: 

// src/money.ts — BR-11
export function roundMoney(value: number): number {
  if (!Number.isFinite(value)) return 0;
  const sign = value < 0 ? -1 : 1;
  return (sign * Math.round(
    Number((Math.abs(value) * 100).toPrecision(12))
  )) / 100;
}

Apply the same normalisation to toPesewas. This is a week-1 task and must land before any sale path is written on either side.

Shared test vectors

The durable fix is a single file that both implementations are tested against, so they cannot silently disagree: 

docs/contract/test-vectors.json
  ├── money            inputs → expected pesewas          BR-11
  ├── quantity         inputs → expected 3dp base units   BR-12
  ├── weightedAvgCost  (onHand, avg, recvQty, recvCost) → new avg   BR-4
  ├── receiptNumber    (outlet, terminal, seq) → formatted string   BR-6
  ├── barcodeResolve   code → { productSku, unitName, factor }      FR-PROD-04
  └── permissions      role → resolved code list, plus overrides    §6

read by →  src/contract-check.ts        (npm run check)
read by →  RulesVectorTest.java         (mvn test)
Non-negotiable

Neither implementation gets its own private expectations. If a vector needs to change, it changes in one file and both sides fail together until they agree. This is the only mechanism keeping a TypeScript frontend and a Java backend honest about money.

06 Permissions

A role supplies a baseline; per-user overrides grant or revoke individual codes on top of it FR-USER-03. Resolution happens server-side on every request.

Discrepancy to resolve in week 1

permissions.ts defines 33 codes. The PRD §6 matrix documents 31. The two extras are stock.transfer (Stage 3, stock movement between outlets) and customer.credit (Stage 2, credit sales). The delivery plan compounds it by referring to "the 31 codes".

Recommendation: seed all 33, so no migration is needed when Stage 2 and 3 land, and leave the two deferred codes ungranted on every role including Owner. Then amend contract-check.ts, which currently asserts the Owner holds every code — an assertion that would otherwise force you to grant capabilities that have no endpoints behind them.

RoleCodesScope
Owner33Whole business, both outlets. Sole holder of user.manage, outlet.view_all, settings.general, product.import
Manager28One outlet, operational. Approves below-floor sales and voids, closes the day
Cashier7Sell, discount to limit, reprint, open and close own shift. No cost, no profit, no reports
Storekeeper7Catalogue and stock. Sees cost, cannot sell, cannot see reports

Enforcement

  • Argon2id for passwords; PINs hashed separately with their own salt NFR-8
  • Method-level @PreAuthorize("hasAuthority('sale.void')") on every mutating endpoint
  • Rate limiting on authentication and approval endpoints NFR-10
  • A guard rejecting any permission change whose subject is the acting user BR-16
  • Cashier's sale.view_all resolves to own-sales-only, not a blanket grant
Local-first changes the threat model

The database now sits on a shop-floor PC. Physical access is data access. Set a real Postgres password rather than trust authentication, run the service under a dedicated Windows account, and do not enable remote connections. Full disk encryption is worth raising with the client but is their call, not a Stage 1 deliverable.

09 Printing

Receipt layout is specified in PRD §9. The printer is a USB thermal unit on the same machine, addressed through the Windows spooler in RAW mode.

  • Receipt begins printing within one second of sale completion NFR-3
  • Printer, paper width, test print and auto-print are configurable per terminal FR-RCPT-08, FR-SET-05
  • A sale completed with the printer switched off is never lost; the receipt prints on retry §11.2
  • Reprints are permitted under sale.reprint and are marked as reprints on the slip
Buy the printer in week 1

This was the cheapest de-risking item in the original plan and it still is. Without a physical ESC/POS device on the desk, acceptance criterion 2 cannot be signed off and printing stays unknown until install day. Nothing about local-first changes that.

10 Backup & recovery

This is the real cost of local-first, and the one place the architecture is weaker than managed hosting. It is solvable, but only if it is built in week 2 rather than week 6.

RequirementTargetMechanism
NFR-6Daily off-site, 30-day retentionNightly pg_dump, gzipped, uploaded to Cloudflare R2 with retry until acknowledged
NFR-7RPO 15 minutesWAL archiving to a second local disk, plus the nightly off-site dump
NFR-7RTO 4 hoursReinstall the MSI on a replacement PC and restore the most recent dump
FR-SET-07Visible backup statusSettings surfaces last successful backup and restore history
The failure this prevents

A counter PC's disk dying takes that shop's entire trading history with it. There is no managed provider standing behind this any more. The nightly upload is not a nice-to-have — it is the only thing between the client and total loss, and it must be proven working at both shops before go-live, not assumed.

A restore is actually performed during week 6, into a scratch database, and the result recorded. An untested backup is not a backup.

11 Packaging & install

jpackage produces a Windows MSI carrying a trimmed JRE, so the counter PC needs no Java installed and no runtime to keep patched.

  • Spring Boot registers as a Windows service and starts on boot — the shop must be able to trade after a power cut without anyone running a command
  • Postgres installs alongside as its own service, with a generated password stored in the app's configuration
  • First run walks through outlet identity, terminal code, receipt sequence block and printer selection
  • A desktop shortcut opens Chrome directly at localhost:8080 in kiosk mode
Updates are now a site visit

Every fix means touching two Windows machines instead of pushing to a host. Budget remote-desktop sessions through hypercare, and consider a version check that tells the operator an update is available rather than discovering it on a phone call.

How the owner sees both shops while away

This is the question local-first has to answer, and it has a cheaper answer than full replication — because of what the requirement actually asks for. FR-RPT-01 wants "today's sales, estimated profit, expected cash, low stock count, open shifts", separately and combined. That is five numbers per outlet. A summary, not a drill-down.

Phase 1 is a stepping stone, not a throwaway — phase 2 extends the same push over the same connection to the same instance. Both reuse the codebase, so there is no second system to learn or maintain.

Why this beats the original cloud plan

Under the old architecture, the cloud instance going down stopped both shops trading. Under this one it means the owner's dashboard is stale until it returns — the tills never notice. The cloud has moved from system of record to optional convenience, which is the risk posture local-first was bought for.

Two details that decide whether it is trusted

  • Outbound only. Shops push; nothing connects inward to a counter PC. No port forwarding, no static IP, no attack surface on a machine sitting on a shop floor. A per-outlet token is sufficient authentication.
  • Show the staleness. "Inco — as of 14:32", and when a shop's connection drops, "Radiance — last seen 2 hours ago". The dashboard must never imply live figures it does not have. An owner trusting the number matters more than the number being fresh.
Still needs client sign-off

PRD §1.2 promises "one owner's view of the whole business" and the installation plan's exit condition is that the owner sees both outlets on one dashboard. Phase 1 delivers that — but it sits outside the six weeks, and until it ships the owner sees one shop at a time. Agree in week 1 whether phase 1 is inside this engagement or quoted separately.

13 Six weeks

Same six weeks, healthier shape. The offline queue and the separate print service are gone — roughly two weeks of the riskiest work — replaced by about one week of predictable packaging and backup work. Week 6 is no longer a cliff.

Week 1

Foundations

  • Spring Boot skeleton; Flyway migrations from §7 with UUID keys, outlet_id, synced_at
  • rules package ported; test-vectors.json read by both sides
  • money.ts rounding fix applied and re-frozen
  • Argon2id passwords and separate PIN hashing; sessions; the 33 permission codes
  • Resolve the 31-vs-33 discrepancy; reword acceptance criterion 4; order the thermal printer

Exit A cashier signs in against the local API and is refused a manager-only endpoint by the server. Both test suites read the same vector file and pass.

Week 2

  • Products, units, conversions, unit-bound barcodes; outlet-scoped search
  • stock_level and inventory_movement; goods receipt with weighted average cost
  • Import endpoint reusing the frontend's validation rules
  • Nightly backup to R2, working and verified — moved forward from week 6

Exit Receiving three drums of 100 m cable moves stock to 300 m against the real database, quantity equals the sum of movements, and last night's dump is in R2.

Week 3

Selling

  • Sale, sale item, payment; idempotency on both UUIDs
  • Atomic decrement with row lock and availability check
  • Receipt number issued from the terminal's pre-allocated block
  • Void with reversing movements; below-floor approval recorded; flagged oversell path

Exit A goods receipt on a tablet and a sale at the till, hitting the same product at the same moment, produce one correct outcome. The same sale submitted twice records once.

Week 4

Cash, parties, reporting

  • Shifts, blind count, variance, cash movements, end of day
  • Customers and suppliers
  • The sixteen reports from frozen costs; gross profit, COGS, discount and void logs

Exit A blind close records variance against the cashier, demands a note past the threshold, and the day reconciles.

Week 5

Integration & printing

  • Every view off mock state onto the API; loading, error and retry throughout
  • ESC/POS output on the real printer; per-terminal configuration; reprints
  • Vite build served from the JAR; kiosk shortcut
  • Search under 300 ms against a synthetic 3,000-product catalogue

Exit No component imports mockData, and a full day of trading can be done against a real receipt printer.

Week 6

  • jpackage MSI with bundled JRE and Postgres; Windows service; first-run wizard
  • Nightly stock reconciliation job NFR-17
  • A restore actually performed and recorded
  • All twelve acceptance criteria scripted and repeatable; security pass on every endpoint

Exit A clean Windows machine goes from MSI to a printed sale without a developer present. Power pulled mid-sale, the committed sale survives.

Where the slack went

Backups moved from week 6 to week 2, and printing from week 6 to week 5. Week 6 now holds only packaging and acceptance — work whose shape is known in advance. That is the first version of this plan where the final week is not carrying an unsolved problem.

14 Acceptance

Twelve criteria from PRD §11. Local-first changes what two of them mean, and one is unsatisfiable as written.

Criterion 4 cannot be demonstrated on this hardware

One terminal per outlet AS-4, plus stock_level keyed on (product_id, outlet_id), plus non-overlapping catalogues, means the only two terminals in the system can never touch the same row. Discovering this in week 6 would mean a criterion that cannot be signed off.

Proposed wording: "A goods receipt and a sale hitting the same product at the same outlet simultaneously produce one correct stock level, or a clear refusal if stock is insufficient." That tests the same lock on a collision that genuinely occurs.

Criterion 10 needs restating

There is no network in the sale path any more, so "disconnect mid-sale" is now a power cut, not a dropout. Restate it against NFR-5: pull power mid-sale, and on restart the committed sale is present exactly once and the uncommitted one left no trace.
